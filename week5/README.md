“비정형 데이터면 LLM, 정형 데이터면 코드” 라는 기존의 생각을 이번에도 동일하게 적용하려고 했습니다. 그런데 채용 공고 추천 시스템을 짜다 보니, 틀어진 부분이 있었습니다. 그래서 AI를 쓰지 않기로 결정을 했고 설계까지 다 해 둔 상태에서 폐기했습니다.
LLM 사용을 들어낸 경험과 적용한 경험을 거치며, LLM의 사용을 결정할 때 이런 기준을 세웠습니다.
“결정론적 문제의 종류가 코드로 감당할 만큼 범위가 제한되느냐, 아니면 너무 많아서 비결정론적 문제로 볼 수 있느냐”
범위를 제한할 수 있으면 LLM 자체가 필요 없어지는데, 맞닥뜨렸던 사례 네 가지와, 거기서 뽑은 LLM 적용 기준, 그 기준을 따른 효과까지 차례대로 풀어 보겠습니다.
1. LLM 사용을 들어낸 첫 번째 사례 — “URL만 주면 알아서 크롤링하는 에이전트”
채용 공고 사이트는 회사마다 DOM 구조와 형태가 제각각입니다. 각 사이트에 맞춘 크롤러를 일일이 짜는 대신, 비정형 데이터를 유연하게 해석하는 LLM의 적응력을 활용하려 했습니다. URL만 던져 주면 에이전트가 알아서 페이지를 탐색하고 정제해 정형 결과를 내도록 만드는 것이 목표였습니다. 이 장점을 극대화하면 최소한의 리소스로 모든 형태의 웹페이지를 커버 할 수 있을 것이라 기대했습니다.
이 시도는 토큰 비용이라는 단순한 벽에 부딪혀 폐기됐습니다. 일반적인 채용 페이지 한 장이 수만 단위의 입력 토큰을 소모했고, 동적 로딩이나 화면 변화를 따라가는 과정에서 컨텍스트가 누적되며 비용이 기하급수적으로 늘었습니다
여기까지가 당시 회고였습니다. “비용이 너무 컸다.”
한참 뒤에야 그 회고가 한 단계 부족했음을 알게 됐습니다. 채용 포털 한 곳을 타겟팅하기로 정하는 순간, 다뤄야 할 페이지 구조가 코드로 감당할 수 있는 몇 가지 (포털 한 곳의 페이지 패턴 몇 종류) 로 줄어들었기 때문입니다. 이때 LLM의 효용은 비용이 비싸서 줄어든 것 이 아니라, 풀어야 할 문제 종류가 너무 적어 LLM의 적응력이 더 이상 가치를 만들지 못해서 사라진 것이었습니다.
결정론적 문제 그 자체 (특정 DOM에서 특정 필드를 추출) 에 코드가 적합하다는 사실은 처음부터 알고 있었습니다. LLM을 고려한 진짜 동기는 결정론적 문제 여러 개 를 처리해야 한다는 것이었지만, 채용 포털의 존재가 코드로 처리 가능한 수준으로 줄여 버렸습니다.
2. LLM 사용을 들어낸 두 번째 사례 — 회사명 정규화 LLM 파이프라인
추천 시스템 후반에 또 한 번 LLM을 끼워 넣으려 했습니다. 사용자가 자유롭게 입력한 회사명을 사내 회사 ID에 매핑하기 위한 3단계 파이프라인이었습니다.

```
[ 사용자 회사명 입력 ] ── (예: "스마일게이트", "휘찬게임즈")
        │
        ▼
[ 1단계: 사전 및 캐시 조회 ] ── (동의어 사전 / Redis 캐시)
        │
        ├─ 매핑 존재 ──► 처리 완료
        │
        ▼ 매핑 없음
[ 2단계: 후보군 추출 ] ── (유사도 검색 Top-N)
        │
        ▼
[ 3단계: LLM 정밀 매칭 ] ── (입력 원문 × Top-N 교차 검증)
        │
        ├─ 정답 존재 ──► 동의어 사전 추가 → 처리 완료
        │
        └─ 정답 없음 ──► Miss 로그 + 예외 처리
```

설계 자체는 그럴듯했으나 폐기됐습니다.
백엔드에서 비정형 입력을 정규화하려고 LLM 비용을 지불하는 대신, 입력 폼에 제약을 걸어 비정형 입력 자체가 생기지 않게 하는 쪽이 더 단순했습니다. 사용자에게 자유로운 입력을 허용하지 않고, 크롤러가 이미 모아 둔 회사 목록에서 골라 선택하게 하면, 사용자 입력 회사명을 시스템에서 사용 중인 회사 코드로 매핑하는 과정 자체가 애초에 일어날 일이 없어집니다.
이 결정이 가능했던 배경으로, 데이터 생산자(채용 공고를 등록·크롤링하는 측) 가 이미 정규화된 회사 목록을 가지고 있었습니다. 소비자(사용자 입력 측) 는 생산자가 만든 그 목록을 단순 참조하면 끝이었고, 양쪽에 정제 파이프라인을 중복으로 둘 이유가 없었습니다.
결과적으로 시스템이 다루는 문제가 “언제든 새로운 값이 들어올 수 있다는 열린 공간의 불확실성” 에서 “이미 인지한 데이터 풀 안에서만 선택하는 닫힌 공간의 문제” 로 재정의됐습니다. 해결해야 할 문제 자체가 소멸한 셈입니다.
닫힌 공간으로 만들면 문제 자체가 결정론적인 문제로 바뀌고, LLM을 사용하는 것보다 코드와 시스템으로 제어하는 게 더 효과적입니다.
3. 두 사례에서 뽑은 LLM 적용 기준
두 사례를 묶고 보니 같은 형태의 판단을 거치고 있었습니다. 정리하면 다음과 같습니다.

* 결정론적 문제 자체는 원래 코드가 잘 푸는 영역입니다. 다만 결정론적 문제 종류의 묶음이 커지면 그게 비결정론적인 문제처럼 다가오기 시작하고, 이 때에 LLM의 적응력이 효과적입니다.
* 종류가 코드로 감당할 만큼 적게 추려진다 → 코드. 비용·재현성·검증 가능성 모두 코드 우위입니다.
* 종류가 사실상 끝이 없거나, 유한하더라도 코드로 감당하기엔 너무 많다 → 두 가지 선택지가 있습니다. - 비결정적 문제로 간주하고 LLM에 위임 — 적응력을 사용합니다. - 문제 종류를 코드로 감당할 만큼 범위를 제한한 뒤 코드로 처리. 회사명 정규화 사례에서 “입력을 닫힌 공간으로 묶기” 가, 크롤링 사례에서 “채용 포털 단일 타겟팅” 이 정확히 이 범위 제한에 해당합니다.
* 종류의 범위를 제한할 수 있는지를 먼저 확인합니다. 이 질문은 LLM 적용 여부보다 앞단의 질문이며, 범위를 제한할 수 있으면 LLM 자체가 필요 없어집니다.
이 기준은 추천 시스템 바깥에서도 같은 형태로 작동합니다. 회사 내부의 부서별 제출 데이터 정제 시나리오를 예로 들면 이렇습니다.

* 단일 부서가 형식을 자주 바꾼다: 시점마다 형식이 달라져 다뤄야 할 결정론적 문제가 사실상 끝없이 늘어남 → LLM이 유효합니다.
* 각 부서마다 형식은 다르지만 부서별로는 고정: 부서가 몇 개든 그 수만큼만 결정론적 문제가 생기고, 코드로 감당할 수 있는 규모라면 코드로 충분합니다.
핵심은 “형식이 여러 개냐” 가 아니라 “그 여러 개가 코드로 감당할 수 있는 규모로 추려지는가” 입니다. 종류가 유한하더라도 그 수가 너무 많으면 결국 LLM에 맡기는 게 현실적입니다.
4. LLM을 활용했던 두 가지 사례
4–1. 채용 본문 정형화
크롤러가 수집한 채용 본문 텍스트는 회사·직무마다 분량과 구조가 모두 다른 전형적인 비정형 데이터입니다. 결정론적 문제의 종류가 사실상 무한합니다. 이런 데이터를 한 번 정형으로 정리해 두면, 이후 매칭·검색·집계 같은 후속 처리를 정규화할 수 있고 같은 입력에 대해 같은 결과를 보장합니다.
이 본문을 LLM에 넘겨, 지원자에게 요구되는 항목을 다음 세 카테고리의 짧은 문장 배열로 정형화합니다.

```
- "experience":  요구/우대 경력      (예: "Unity 3년 이상")
- "competency":  보유 기술/스킬/도구  (예: "C# 숙련", "Git 협업")
- "trait":       인성/태도/성향       (예: "주도적인 문제 해결")
```

본문을 임시 파일에 적은 뒤 `gemini -p <prompt> @<body_file> -o text` 형태로 처리하고, 결과를 한 게시물당 한 행으로 데이터베이스에 저장합니다. 매칭 단계가 별도 가공 없이 그대로 가져다 쓸 수 있는 형태입니다.
핵심은 프롬프트로 출력 스키마를 고정하는 Structured Output 패턴 입니다. 다음 단계인 매칭 — 추출된 항목을 사용자 프로필과 비교해 공고를 추천할지 정하는 코드 — 은 LLM 응답을 정형 데이터로 바로 받습니다.
4–2. 이미지 본문 OCR
채용 공고 중에는 본문이 이미지로만 들어 있는 경우가 있습니다. 텍스트 본문이 없는 게시물은 OCR 워커가 이미지를 텍스트로 바꾼 뒤 본문에 합쳐 둡니다.
처음에는 PaddleOCR(별도 Python 런타임 + 모델 파일 관리) 을 썼는데, 로컬 환경의 컴퓨팅 리소스가 OCR 모델을 충분한 속도로 구동하기에 부족했습니다. gemini-cli는 추론을 구글 서버에 위임하므로 로컬 부담 없이 처리가 가능했고, 마침 위 extractor가 이미 같은 방식으로 호출하고 있던 도구라 자연스럽게 통일됐습니다. 결과적으로 두 LLM 사용처가 같은 도구를 같은 방식으로 호출합니다.
OCR도 결국 “비정형(이미지) → LLM 정제 → 정형(텍스트)” 흐름이라 extractor와 같은 패턴의 두 번째 적용 사례입니다
5. 효과 — 이 기준을 따른 결과 시스템에 남은 것
결정론적이면 코드, 비결정론적 문제는 LLM — 이 기준을 따른 결과 네 가지가 시스템에 남았습니다.
1) 외부 의존성 단순화. PaddleOCR을 떼고 gemini-cli로 단일화하면서, 두 LLM 사용처(본문 정제·OCR) 가 같은 방식으로 도구를 호출하게 됐습니다. 운영 비용도 줄었고, 유지보수에 유리한 구조가 되었습니다.
2) 매칭 기준의 형태가 LLM 정제 단계에서 결정. 매칭 코드는 정해진 JSON 스키마(experience / competency / trait) + 직무 코드 + 정규화된 회사 ID + 사용자 선호도·경력 만 받습니다.
3) 단순 비교 가능한 매칭 기준. 법인 식별자(주식회사·(주) 등) 를 제거하는 회사명 정규화는 코드로 처리합니다. 비정형 입력을 생산자(크롤러) 단계에서 미리 정규화하여, 소비자(매칭 로직) 측은 단순 비교만 합니다.
6. 한계
결정론적이면 코드, 비결정론적 문제는 LLM 이라는 기준이 모든 LLM 사용의 적합도를 결정하지는 않습니다.
매칭 단계에 LLM을 또 둘지는 이 기준으로 미리 결정할 수 없습니다. 매칭 결과를 본 뒤에 결정할 수 있습니다.

* 결과 순위 보정, 사용자가 자유롭게 적은 키워드 해석, 본문과 입력의 의미적 유사도
또 하나 짚어 둘 부분이 있습니다. 글에서 다룬 두 사례 모두 “비결정론적 문제인 줄 알았지만 범위를 제한하는 경우 결정론적 문제로 전환되는” 케이스였습니다. 처음엔 비결정론적으로 보이던 문제도 채용 포털 / 입력 폼 제약 같은 제한을 거치면 결정론적 문제로 바뀌고, 그 시점에 LLM이 필요 없어졌습니다.
“비결정론적인 문제가 맞는지 LLM 적용 결정보다 앞에서 한 번 더 확인하자”
7. 마무리
평소에 알고 있던 답은 “비결정론적인 문제는 LLM, 그 외는 코드” 였습니다. 이번에도 같은 개념으로 적용하려고 했으나 문제를 잘못 정의하고 있었습니다. 비결정론적인 문제가 아니라 결정론적인 문제였습니다. 채용 포털 한 곳으로 타깃을 좁히거나 자유로운 입력을 한정된 목록 선택으로 바꾸는 순간, 다뤄야 할 종류가 코드로 감당할 수 있는 규모로 줄어들었습니다.
LLM을 활용할 때 문제 정의를 잘 하는 능력이 중요합니다. 지난 스터디에서 문제 정의를 중심으로 진행했고, 이번에는 문제 해결에 LLM을 잘 활용해보자는 목적이 있었는데, 결국 문제 정의의 중요성을 다시 깨닫게 되는 순간이었습니다.
“문제를 정의할 때 다양한 각도로 문제를 분석하여 보다 정확한 정의를 해야겠습니다.”
